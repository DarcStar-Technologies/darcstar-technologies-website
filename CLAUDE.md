## Project

DarcStar Technologies marketing website — SvelteKit (Svelte 5) on **Cloudflare Pages**. Still close to a fresh `sv create` scaffold; most of `src/routes` and `src/stories` is template/demo content.

Non-negotiables:

- Package manager is **pnpm** (pinned in `packageManager`; `.npmrc` sets `engine-strict=true`). Use `pnpm`, never `npm`.
- **Svelte 5 runes only** — runes mode is forced project-wide. No legacy `export let`. See [docs/svelte.md](docs/svelte.md).

## Lessons

Durable gotchas — keep to one line; link to the doc that carries the detail.

- Keep `@tailwindcss/forms`; Skeleton's form components depend on it. → [styling](docs/styling.md)
- Site is **dark-only**: `data-mode="dark"` hardcoded on `<html>` in `app.html`, no toggle. Distinct from `data-theme` (palette). → [styling](docs/styling.md)
- Palette is the **custom `darcstar` Skeleton theme** (`src/themes/darcstar.css`); regenerate ramps via `node scripts/gen-theme.mjs`, don't hand-edit. → [styling](docs/styling.md)
- The RGB **color-charge triad has ONE source** — the theme (`tertiary`/`secondary`/`primary` = R/G/B). `--charge-*` and `CosmicBackdrop`'s canvas both derive from `--color-*-500`; never re-type the hexes. → [styling](docs/styling.md)
- **Brand type is self-hosted** (Space Grotesk / Inter / JetBrains Mono via Fontsource `@import` in `layout.css` — CSS, not a JS import, or svelte-check chokes). Body/heading tokens live in `gen-theme.mjs`; mono/sans in `layout.css` `@theme`; bare `<h1>`–`<h6>` need the base-layer rule (Skeleton styles only `.h1`–`.h6`). → [styling](docs/styling.md)
- **Every page's hero uses one pattern**: `eyebrow` → `#helix-slot` (CosmicBackdrop centres AND SIZES the RGB helix there — the slot's **height** caps the helix amplitude, `amp = min(span*0.11, slotH*0.42)`) → heading+lede in a **`glass-card`**; never a bare centered heading. The **homepage** keeps the panel fully **below** the helix (the helix is the centrepiece). **Every other page** — the shared `PageHero` (`/news` · `/research` · `/people` + their detail pages, `/privacy` · `/terms`) and `/about` — pulls the panel **up by nearly the full slot height** (`min-[360px]:-mt-[min(23vw,17.5rem)]` — a hair less than the slot's own `min(25vw,19rem)`, leaving a small gap below the eyebrow; still can't over-pull) so the hero starts **just below the eyebrow with breathing room, its top slightly above the helix's start**; the helix becomes a backdrop behind/beside the frosted panel (its wider outer arcs peek out at the sides). Keep the `#helix-slot` height — it caps the helix amplitude, so shrinking it shrinks the helix. → [styling](docs/styling.md)
- **Keyboard focus is ONE ring plus `hover-focus:` (DAR-57)** — nothing in the repo defined a focus style, so every link fell back to the UA ring on surfaces where every other state is designed (the theme's `--anchor-text-decoration-focus` is a red herring: it only feeds Skeleton's `.anchor` **class**, which this site never uses; Skeleton leaves the global rule to the app, commented example and all). Now one `@layer base` rule outlines `a`/`button`/`summary`/`input`/`select`/`textarea` in `2px solid var(--color-primary-400)` — **every interactive element, not just anchors**, because branding the link ring and leaving buttons on the UA default trades a missing indicator for an inconsistent one. Five things worth keeping: (1) `@layer base` is what lets a surface that OWNS its focus state still win (`glass-field`'s recessed ring, `/admin`'s `focus-visible:ring-*`), making the rule **opt out only by REPLACING it**; (2) it's an explicit element list, not a bare `:focus-visible`, because Kit focuses `<body>` after a client-side navigation (asking for `focusVisible: false`, not honoured everywhere) and a bare selector would outline the whole page; (3) the ring says WHERE focus is, `hover-focus:` says the thing IS interactive — a `hover:`-only affordance tells a mouse user that and a keyboard user nothing, so the variant fires on both and its `@media (hover: hover)` guard is load-bearing (Tailwind's own `hover:` compiles with it; a raw `&:hover` would start applying hover styles on touch). It composes — `group-hover-focus:` for the news card; (4) a global rule has NO call sites, so `focus-visible.e2e.ts` is the only thing that can prove it fires: real **Tab** presses (`:focus-visible` is a heuristic under `element.focus()`), every link/button stop asserted, plus a **minimum stop count** so a walk finding nothing fails rather than passing vacuously; (5) Tailwind v4's `transition-colors` includes **`outline-color`**, so the ring fades in from `currentColor` over 150ms — invisible to a human, but it makes a computed-style read taken right after focusing report the element's text colour, which is why the walk waits for each stop's transitions to settle. → [styling](docs/styling.md)
- **Shared class strings live in `$lib/styles.ts`, never a component's `<script module>`** — form chrome (`fieldClass`/`submitButtonClass`/`fieldLabelClass`/`fieldHelpClass`) plus the link treatments. A route that needs only the string shouldn't have to import a form component to get it, and a control that renders its own label (GlassSelect's native fallback, step 4A's textarea) can't drift from one that delegates. → [styling](docs/styling.md)
- **Raised frosted surfaces share a `@utility glass` base**; variants (`glass-nav`/`glass-card`/`glass-btn`) `@apply glass` + deltas. A Tailwind v4 `@apply` **inlines styles but never adds the applied class name** — a `class="glass-card"` panel carries no `glass-panel` token, so `querySelectorAll('.glass-panel')` matched nothing and the sheen silently missed every panel (#108). Fix + rule: the sheen selects **structurally** — `[class*="glass-"]:not(.glass-field):not(.glass-menu)` (`glass-sheen.ts`) — but that's a **substring** match, so name new raised surfaces `glass-*` and don't reuse `glass-` in a non-raised token (or extend the `:not(...)`). → [styling](docs/styling.md)
- `pnpm preview` runs the built worker on the real Workers runtime (Wrangler), not `vite preview`. → [commands](docs/commands.md)
- **The preview port is derived per checkout, and e2e never reuses a running server (DAR-79)** — `pnpm preview` and `playwright.config.ts` both read `scripts/preview-port.mjs` (main checkout `4173`; each linked worktree a stable slot in 4174–4272, hashed from its path; `PREVIEW_PORT` overrides, and a non-port value is refused rather than ignored). They used to hardcode 4173 each, and Playwright's `reuseExistingServer` defaults **on** locally — so a preview running in a **sibling worktree** answered the whole suite and it came back green for someone else's branch. Reuse is off now (`E2E_REUSE_SERVER=1` opts back in, warning that the results describe whatever is listening), and a busy port names its owner's **pid + cwd**, because the reflex fix is a `pkill` that kills another session's server. Three mechanics worth keeping: the config is re-imported in **every Playwright worker** — by then our own webServer holds the port, so any port check must be gated on `TEST_WORKER_INDEX === undefined` or the suite fails against itself; `workerd` is wrangler's **grandchild**, so kill the **tree root** (killing the socket owner just makes wrangler respawn it) and a SIGKILLed parent leaves it holding the port under `ppid 1` forever — the source of the stale servers, which `preview.mjs` now reaps three ways (forward SIGTERM, SIGKILL a wedged tree, and ask the port whether something outlived the child, since leftovers stop being its descendants the moment it dies). **Finding that tree root by "walk up while the ancestor is node" walks straight OUT of the tree into whatever supervises it** — under vitest that's the test runner, and the reaper SIGTERMed it (a mutation test proved it: `Terminated`, exit 143); the stop condition must be conjunctive, argv[0] **and** a preview-shaped command line; and CI is a main checkout (`.git` is a **directory**, a linked worktree's is a **file**), which is what keeps `test.yml`'s hand-written `ORIGIN=http://localhost:4173` true — pinned by a spec, since one half is YAML. → [commands](docs/commands.md)
- Run `pnpm gen` after changing `wrangler.jsonc` bindings **or `.env.example`** to refresh the `Env` type — generation is **deterministic** (DAR-49): env-var names come from `.env.example` (never `.env`), volatile wrangler output is normalized, and the `check` CI job drift-guards the committed `worker-configuration.d.ts`. Never run `wrangler types` directly. → [deployment](docs/deployment.md)
- **Prod and dev are SEPARATE Turso DBs, one per Cloudflare Worker.** Prod Worker (`main`→darcstar.tech) → prod DB; a **separate preview Worker** (`[env.preview]` in `wrangler.jsonc`, non-prod branches, `wrangler versions upload --env preview`) → dev DB; local `.env` → dev DB. Each Worker holds its own `DATABASE_*` secret, so `getDb()` has **no** env logic — isolation is at the secret layer. First-time split runbook + the preview Worker's own secrets are in [deployment](docs/deployment.md#environments--databases). → [deployment](docs/deployment.md)
- Changing the DB schema? Run `pnpm db:generate` + commit the `drizzle/` migration — the **`drizzle` CI check** (+ a pre-commit hook) regenerates offline and fails on drift, gating merge→prod. **Dev DB** applies via `pnpm db:push`; **prod DB** applies via the **`deploy-prod` GitHub Action** which `pnpm db:migrate`s **then** `wrangler deploy`s on push to `main` (`PROD_DATABASE_*` + `CLOUDFLARE_API_TOKEN`/`CLOUDFLARE_ACCOUNT_ID` secrets), so a failed migration **blocks the deploy** (migrate-before-deploy; Workers Builds does previews only, prod auto-deploy disabled) — never `db:push` prod. An existing `db:push` prod DB needs a one-time `pnpm db:baseline` so migrate is forward-only (skips replaying `0000`). → [deployment](docs/deployment.md)
- `checkJs` is **off** — generated Paraglide `.js` clashes with the Cloudflare `Request` global; no hand-written `.js` exists, so `.js` bodies aren't checked. → [i18n](docs/i18n.md)
- **All UI copy lives in Paraglide messages** (`messages/*.json`); the `local/no-raw-text` ESLint rule blocks hardcoded `.svelte` text/attrs (Wordmark exempt). `es` is untranslated → non-base locales are `noindex` via `Seo.svelte`'s `TRANSLATED_LOCALES` flag; hreflang deferred until `es` is real. → [i18n](docs/i18n.md)
- **A non-base catalog holds ONLY translated keys (DAR-53)** — `es.json` was a byte-identical copy of `en.json`, so Paraglide compiled two identical bodies per message; omitting a key compiles the base-locale fallback as a free alias (`const es_x = en_x`) with identical output (−39 KB raw / −6.8% of the client bundle, but only −172 B gzipped — the win is parse+cache, not wire). The convention was documented before and drifted anyway, so it's now `message-catalogs.spec.ts`: **never re-add a key equal to the base value** (true even when the translation legitimately matches — omitting renders the same text for less) and **never add a key the base lacks** (Paraglide compiles an orphan's _base_ variant as the quoted key name, so a typo silently no-ops the translation while English still looks right). Nothing warns — there is no message-lint module in `project.inlang/settings.json`. The spec derives its catalogs by glob, but `evidence-boundary`/`safety-language` scan `en`+`es` **by name**, so it also pins the locale set. → [i18n](docs/i18n.md)
- e2e builds + previews the Cloudflare bundle; match the vitest project to your filename (`client` / `server` / `storybook`). **Six required CI checks gate merge→main** (lint, commitlint, migrations in sync, check, unit tests, e2e — DAR-49); both test suites are **hermetic** (no `.env` in CI), keep new tests that way. → [commands](docs/commands.md)
- **A red unit run records itself — don't keep the log (DAR-90)** — one run reported `1 failed | 590 passed` through a `grep` pipe and the reflex re-run destroyed the only copy of the name, so the evidence moved into the machine: a reporter (`scripts/vitest-failure-report.ts`, wired at the **root** `test.reporters` — not a per-project option) writes `test-failures/<ISO>-<pid>.json` on a red run and **nothing** on a green one, so anything in that directory is by construction a failure. Four load-bearing properties: the filename is **unique per run**, because the built-in `json`/`junit` reporters take a FIXED `outputFile` and would re-create the exact "re-running destroys it" defect one directory further from the terminal; a **collection error is recorded even with zero failed test cases** (a module throwing at import makes a red run whose `allTests('failed')` is empty — a reporter walking only failed cases writes "no failures" for it, which misleads worse than silence); the report carries the **10 slowest tests of the run**, since `loadavg` alone can't separate "the box was busy" from "the test is broken" but a baseline can; and every entry point is **fail-soft**, because a reporter that throws turns a green run red. One trap: a CLI `--reporter=…` **replaces** the configured list (so `--reporter=verbose`, the flag you'd type while chasing a flake, silently switches recording off, and `--reporter=default` does NOT restore it) — name the module itself as a second `--reporter`, which is what its default export is for. Conformance to vitest's classes is structural — the builder takes minimal interfaces so the spec needs no casts, and the reporter's typed `onTestRunEnd` passing real `TestModule`s is what makes an API drift a `pnpm check` error (mutation-proven). Measuring also **refuted DAR-90's own leading theory**: `preview-port.spec.ts`'s `descendants` runs in **121 ms**, nowhere near its timeout, while the tightest margin is the **browser** projects — the same test measured **914 ms and 2346 ms on one machine** (2.6× run-to-run variance, 2.1× margin against the 5 s default at the slow end), which is why `client`/`storybook` set `testTimeout: 15_000` and `server` keeps the default. → [commands](docs/commands.md)
- Use the Svelte MCP (list-sections → get-documentation) for Svelte/SvelteKit questions; run svelte-autofixer on any Svelte you write. → [svelte](docs/svelte.md)

- **SEO discovery surfaces (DAR-48)** — `/sitemap.xml` is a worker route (static `STATIC_PATHS` + Sanity slugs; **new indexable route → add it there + to the security-headers `AUDITED_PAGES`** — a route-enumerating e2e fails loudly if the sitemap is forgotten); robots.txt hardcodes the prod sitemap URL (static asset). JSON-LD: pure builders in `$lib/jsonld.ts` — **keep it dependency-pure: the root layout imports it (site-wide bundle)**, so pages pre-resolve image URLs via `imageUrl` (`$lib/sanity/image.ts`); **Organization ships from the root layout** (deliberate — not OG tags), page nodes via `<Seo jsonLd>`; the "locale is real" flag `TRANSLATED_LOCALES` lives in `$lib/seo.ts`, shared by Seo + sitemap + e2e. → [seo](docs/seo.md)
- **A CMS page's head is one mapper, and "hide from search engines" is TWO surfaces (DAR-71)** — the detail pages don't hand-map Sanity's `seo` object onto `<Seo>` props; they spread `contentSeo(doc.seo, fallbacks)` (`$lib/sanity/content-seo.ts`), because the per-page copy-paste is exactly how `noIndex` came to be fetched, typed, and **dropped at both render sites** (new `seo` field → wire it there, never at a call site). A Svelte spread **does not reject unknown props**, so the mapper returns `Pick<SeoProps, …>` against `Seo.svelte`'s exported props to make a _misnamed_ key a compile error; an _omitted_ key still type-checks (every prop is optional) and is caught only by `content-seo.spec.ts` — both guards are load-bearing. Honoring the toggle needs the robots meta **and** a `seo.noIndex != true` filter on `sitemapEntriesQuery` — noindex alone still advertises the page to crawlers. Polarity is **fail-open** in both (`=== true` / `!= true`, never `== false`): hiding needs a POSITIVE signal, and since no document sets `seo` at all, the inverse would de-index the site in one deploy. The rule can't be single-sourced (one half is GROQ), so it's pinned twice — `content-seo.spec.ts` + `queries.spec.ts`. Hidden ≠ unpublished: the page stays live and listed on `/news` · `/research`. → [seo](docs/seo.md)
- **`canonical` and `og:url` are NOT the same value (DAR-70)** — they were one derived expression in `Seo.svelte` until third-party paper pages needed to canonicalize to arXiv/the publisher (they quote the source abstract verbatim → duplicate content). Only `<link rel="canonical">` is overridable; **`og:url` always stays this page's own URL**, or every social share of our page would carry arXiv as its graph identity. Precedence: editor's `seo.canonicalUrl` → the page's derived `paperSourceUrls(paper)[0]` (`$lib/jsonld.ts`, ordered `url` → DOI → arXiv, **shared with the ScholarlyArticle `sameAs`** so the doi.org/arxiv.org templates exist once) → self. **Both** inputs pass the same `isHttpUrl` gate (absolute http(s), no whitespace — `new URL` turns a prose-filled `doi` into a well-formed 404, and the Studio's own url validation is a UI affordance an API write skips); an unusable override falls THROUGH to the derivation. First-party (`darcstarAuthored === true`) stays self-canonical, fail-safe like DAR-52. Canonicalized pages **stay in the sitemap**; JSON-LD `mainEntityOfPage` stays our page. → [seo](docs/seo.md)

Needs `RESEND_API_KEY` + a verified Resend domain. `.remote.ts` may live anywhere except `$lib/server`. Run `pnpm db:push` after schema changes (the default apply path; `pnpm db:generate`+`db:migrate` write/apply a versioned `drizzle/` trail when wanted — see [deployment](docs/deployment.md)). → [contact](docs/contact.md)
- **Waitlist v2 data model (DAR-59)** — `/waitlist` keeps its v1 remote-`form` (honeypot + IP throttle + `isNew`-gated emails + anti-enumeration), now with qualification columns for the progressive flow (DAR-58). The optional steps 2–4 are **unauthenticated enrich writes** authorized by a **signed continuation token** (`waitlist-token.ts`, HMAC-SHA-256 over reused `BETTER_AUTH_SECRET`, domain-separated, 24h, **canonical** — one string per id/exp) returned in step 1's response; because the same success shape (token included) is returned for new **and** existing email (anti-enumeration), the token reaches any submitter of a known address, so `applyWaitlistStep` guards with an **explicit per-step column map** (mass-assignment guard — never identity, never another step's answers) and per-field keep-existing. `contact_permission` is **tri-state** (null = not shown / false = declined / true = granted; validator gates on `isPositivePilotInterest`, store keep-existings null so a not-shown submit can't revoke). `consent_updates` is an **unverified single-opt-in claim** (monotonic, `consent_updates_at` provenance) — must **not** drive a send without double-opt-in. Multi-select step fields **must** be named `foo[]` (SvelteKit's form-data conversion throws on a repeated plain name). `role` holds both v1 + v2 slug sets — canonicalize before branching (`canonicalizeWaitlistRole`, DAR-62). → [waitlist](docs/waitlist.md)
- **Waitlist v2 step-3 gate (DAR-62)** — which step comes next is decided **server-side** and shipped in the step response (`next`); the rule lives ONCE in `$lib/server/waitlist-flow.ts` (DAR-63's step-4 fork + DAR-65's classifier reuse it — never restate it), and living under `$lib/server` makes "not client-authoritative" structural rather than a convention. `isCommercialUseCase` = DAR-62's exclusions (researcher/student/investor-advisor, research-education) **plus fail-safe polarity** — commercial needs a POSITIVE signal, so unanswered/unrecognized routes PAST the money questions (matches the epic's "incl. unanswered → branch B"). The gate is **UX, not authorization**: a crafted POST straight to step 3 still validates + stores, because answering buys no privilege. Two mechanics every later step inherits — each response **echoes the submitted token** (verbatim, capped, never re-minted) so the next step's hidden field survives a no-JS re-render, and the enrich is **best-effort** (`applyStepBestEffort` logs a DB failure instead of erroring the visitor's flow — the fire-and-forget-email posture — and **skips the write for a honeypot decoy id**, so trap-tripping bots cost no DB writes and the step e2e stays DB-free). → [waitlist](docs/waitlist.md)
- **Waitlist v2 step-4 fork (DAR-63)** — the flow ends in one of two branches: **A** (active commercial interest → pilot question, and only for a POSITIVE answer a revealed block of deployment-scale free text / contact permission / method / phone) or **B** (research-general → an uncapped "what to send you" multi-select, never money or pilots). The fork reads `evaluation_timeline` **alone** (`step4BranchFor`, near-term → A, everything else incl. unanswered → B) — role gates step 3, not this. Two rules worth keeping: (1) step 3 does **NOT** read the stored row to re-derive the branch — `next` deriving from stored state would be an **enumeration oracle** (the continuation token reaches any submitter of a known email, so `next: 'step4a'` would prove that address is on the list with a near-term timeline); instead step 2 **signs** the branch (`mintWaitlistFlowClaim`, own domain + `f1` prefix on the shared `mintSignedValue` core; DAR-64 widened its payload to carry the CTA audience too) and step 3's form carries it as a hidden field, so it's server-decided AND untamperable. (2) The conditional reveals are **`mounted`-gated `{#if}`s — enhancement, never a gate**: no-JS renders every field, and the server independently emits `contact_permission: null` ("never asked") unless the pilot answer is positive. → [waitlist](docs/waitlist.md)
- **Waitlist v2 confirmation (DAR-64)** — every path ends on `WaitlistConfirmation.svelte` with **one** CTA, and **which** one is a server decision (`confirmationCtaFor`, ordered strongest-signal-first: positive pilot → `/contact`, commercial → `/evidence`, research/investor → `/research`, unknown → `/`, the fail-safe floor). The step-2 decisions that feed it ride in the **signed flow claim** — DAR-63's branch claim generalized to payload `<branch>|<audience>` under a new domain/`f1` prefix, minted once at step 2 and echoed verbatim through steps 3–4 (one claim, not one per fact) — because deriving them from the stored row would be the same enumeration oracle DAR-63 rejected. Two rules: the confirmation is **fixed copy plus a link**, never a summary (internal-only budget/impact/deployment answers have no path there — the e2e fails on a currency figure or those labels), and the pilot CTA is a **real `/contact` anchor** that JS upgrades into the modal (modifier-clicks untouched, `aria-haspopup` `mounted`-gated). The epic's `evaluation_conversation_requested` event is **not fired** — no analytics transport exists; the call site is marked for DAR-66. → [waitlist](docs/waitlist.md)
- **Waitlist v2 lead classification (DAR-65)** — `classifyWaitlistLead` (`$lib/server/waitlist-classify.ts`) buckets a signup into `priority-a|b|c` / `research` / `investor` for `/admin/waitlist`, **computed on read, never stored** (every input is an already-persisted column, so a denormalized copy would only add a migration + a recompute obligation per step write). Four rules: (1) the **money guardrail is the input type's shape** — `economic_impact`/`budget_range` are absent from `WaitlistLeadSignals`, so a self-reported figure _cannot_ be scored (a concrete $25k prospect outranking an anonymous ">$1M" is unit-pinned), and the figures stay on the row detail for human judgement; (2) it **reuses** `audienceFor`/`canonicalizeWaitlistRole`/`isActiveEvaluationTimeline` rather than restating them, or the rubric would judge people by questions they were never asked — and inherits their fail-safe polarity (an empty row is `research`, never a priority band); (3) **internal only** — `$lib/server` makes "no public page can import it" structural, and only the slug vocabulary `WAITLIST_LEAD_CLASSES` is client-safe (in **triage order, so its index IS the sort rank**) because the badge needs a label, exactly DAR-64's CTA split; (4) the epic's optional **Priority-A notification was deliberately NOT built** — the three signals can only complete at a step-4A submit, which the continuation token authorizes for _any_ submitter of a known email, so it would be an unbounded mailbomb into `info@` (the `isNew` gate's problem again) without a null→positive transition guard the `keepExisting` UPDATE doesn't report. The admin view sorts priority-first (stable sort keeps newest-first within a band), filters via a no-JS `?class=` GET with whole-window counts, renders `contact_permission` as the **tri-state** it is, and prints the "internal guess, unverified claims" caveats under the table. → [waitlist](docs/waitlist.md)

- **Waitlist v2 step-write budget (DAR-68)** — steps 2–4 are unauthenticated writes the continuation token reaches for ANY submitter of a known address, and step 1's throttle can't see them (it counts **rows created** per hashed IP; a step adds no row), so a holder could drive unbounded `UPDATE`s at one row. The cap is **per ROW** (a token addresses exactly one row — that's the abuse unit, and it doesn't punish a shared NAT), 20 writes/hour, and it is a **`WHERE` predicate on the `UPDATE` `applyWaitlistStep` was already making** with the counter in two columns on the row itself (`step_write_count`/`step_write_window_at`; SQLite evaluates `SET` against the **pre-update** row, which is what lets the counter read and replace itself in one statement). Three properties are the reason for that shape: (1) **no extra query** — a permitted step costs what it did before and a refused one costs one zero-row `UPDATE`, strictly LESS than the write it replaces, whereas a counter table (better-auth's `rate_limit` was the candidate) spends a read + a write to refuse a write, i.e. protects the DB by hammering it, and gets more expensive exactly as abuse worsens; (2) **no oracle, structurally** — the guard isn't a check that runs before the write and returns a verdict, it IS the write, so no code path exists that could leak token validity: refused / decoy / expired / deleted-row / success are one generic response (`updated: false` is deliberately the same answer as "no such row"); (3) the cap is far **above** a real ceiling (the flow is three writes) rather than snug against it, because the refusal is SILENT — a tight cap would eat a visitor's answers with no error — pinned by a spec that walks the whole flow five times. Fixed, not sliding: a write inside a live window doesn't move its start and a **refused write touches nothing**, so hammering can't extend its own lockout. Two things it does NOT bound, deliberately: request **volume** (edge/WAF territory — rotating tokens sidesteps anything at this layer) and the **funnel insert on the same endpoints**, whose `flow_id` is client-minted so rotating it defeats the composite-key cap (DAR-86 — sign the flow id; gating analytics on the step write would stop counting the skips the funnel exists to measure). → [waitlist](docs/waitlist.md)
