## Lessons

Durable gotchas — keep to one line; link to the doc that carries the detail.

- Keep `@tailwindcss/forms`; Skeleton's form components depend on it. → [styling](docs/styling.md)
- Site is **dark-only**: `data-mode="dark"` hardcoded on `<html>` in `app.html`, no toggle. Distinct from `data-theme` (palette). → [styling](docs/styling.md)
- Palette is the **custom `darcstar` Skeleton theme** (`src/themes/darcstar.css`); regenerate ramps via `node scripts/gen-theme.mjs`, don't hand-edit. → [styling](docs/styling.md)
- The RGB **color-charge triad has ONE source** — the theme (`tertiary`/`secondary`/`primary` = R/G/B). `--charge-*` and `CosmicBackdrop`'s canvas both derive from `--color-*-500`; never re-type the hexes. → [styling](docs/styling.md)
- **Brand type is self-hosted** (Space Grotesk / Inter / JetBrains Mono via Fontsource `@import` in `layout.css` — CSS, not a JS import, or svelte-check chokes). Body/heading tokens live in `gen-theme.mjs`; mono/sans in `layout.css` `@theme`; bare `<h1>`–`<h6>` need the base-layer rule (Skeleton styles only `.h1`–`.h6`). → [styling](docs/styling.md)
- **Every page's hero uses one pattern**: `eyebrow-hero` → `#helix-slot` (CosmicBackdrop centres AND SIZES the RGB helix there — the slot's **height** caps the helix amplitude, `amp = min(span*0.11, slotH*0.42)`) → heading+lede in a **`glass-card`**; never a bare centered heading. The **homepage** keeps the panel fully **below** the helix (the helix is the centrepiece). **Every other page** — the shared `PageHero` (`/news` · `/research` · `/people` + their detail pages, `/privacy` · `/terms`) and `/about` — pulls the panel **up by nearly the full slot height** (`--helix-pull`, a hair less than the slot's own `--helix-slot-h`, leaving a small gap below the eyebrow; still can't over-pull) so the hero starts **just below the eyebrow with breathing room, its top slightly above the helix's start**; the helix becomes a backdrop behind/beside the frosted panel (its wider outer arcs peek out at the sides). Keep the `#helix-slot` height — it caps the helix amplitude, so shrinking it shrinks the helix. Both values are **`:root` tokens in `layout.css`** (DAR-218), not typed at the five call sites — and **naming a Tailwind class in this file EMITS it**: Tailwind v4's automatic content detection scans `CLAUDE.md`, so the old prose spelling of the pull-up was generating a real, unused rule in the production bundle. Quote a token, never an arbitrary-value class. → [styling](docs/styling.md)
- **Keyboard focus is ONE ring plus `hover-focus:` (DAR-57)** — nothing in the repo defined a focus style, so every link fell back to the UA ring on surfaces where every other state is designed (the theme's `--anchor-text-decoration-focus` is a red herring: it only feeds Skeleton's `.anchor` **class**, which this site never uses; Skeleton leaves the global rule to the app, commented example and all). Now one `@layer base` rule outlines `a`/`button`/`summary`/`input`/`select`/`textarea` in `2px solid var(--color-primary-400)` — **every interactive element, not just anchors**, because branding the link ring and leaving buttons on the UA default trades a missing indicator for an inconsistent one. Five things worth keeping: (1) `@layer base` is what lets a surface that OWNS its focus state still win (`glass-field`'s recessed ring, `/admin`'s `focus-visible:ring-*`), making the rule **opt out only by REPLACING it**; (2) it's an explicit element list, not a bare `:focus-visible`, and the reason is the **`tabindex="-1"` containers, not `<body>`** — Kit focusing `<body>` after a client-side nav looks like the risk but was **measured to be a non-issue** (Chromium matches neither `:focus-visible` nor `:focus` on it), while the contact/login dialog panels are `div[tabindex="-1"].glass-card` and a bare selector would ring the whole frosted panel the moment the dialog library focused its content rather than the close button; (3) the ring says WHERE focus is, `hover-focus:` says the thing IS interactive — a `hover:`-only affordance tells a mouse user that and a keyboard user nothing, so the variant fires on both and its `@media (hover: hover)` guard is load-bearing (Tailwind's own `hover:` compiles with it; a raw `&:hover` would start applying hover styles on touch). It composes — `group-hover-focus:` for the news card; (4) a global rule has NO call sites, so `focus-visible.e2e.ts` is the only thing that can prove it fires: real **Tab** presses (`:focus-visible` is a heuristic under `element.focus()`), links/buttons held to the exact ring, **fields held to "looks different focused than unfocused"** (which is what makes the opt-out rule tested rather than merely documented — and note `outline: none` does NOT reset `outline-offset`, so a naive appearance comparison reports a change that renders nothing and a broken field passes), plus a **minimum stop count** so a walk finding nothing fails rather than passing vacuously; (5) Tailwind v4's `transition-colors` includes **`outline-color`**, so the ring fades in from `currentColor` over 150ms — invisible to a human, but it makes a computed-style read taken right after focusing report the element's text colour, which is why the walk waits for each stop's transitions to settle. → [styling](docs/styling.md)
- **Shared class strings live in `$lib/styles.ts`, never a component's `<script module>`** — form chrome (`fieldClass`/`submitButtonClass`/`fieldLabelClass`/`fieldBadgeClass`/`fieldLegendRowClass`/`fieldHelpClass`/`checkboxClass`) plus the link treatments. A route that needs only the string shouldn't have to import a form component to get it, and a control that renders its own label (GlassSelect's native fallback, step 4A's textarea) can't drift from one that delegates. **The convention was documented and drifted anyway** (DAR-218) — five strings re-typed verbatim, **four of them in files that already imported from the module**, because a module with no consumer list makes a hand-written copy indistinguishable from a route that never needed it: `styles.spec.ts` now holds every `class="…"` literal in `src` against a **superset** test (a copy plus `mt-2` is the same defect one token out), reading the module by **importing** it rather than parsing it, so changing how a string is BUILT can't quietly narrow the scan. Two lessons the fixes carry: an idiom is only shared if **every part** of it is exported — `fieldLabelClass` described its "optional" badge in prose while exporting only the row, so the badge was hand-typed at all 7 sites — and a **subset** copy is invisible to this rule (GlassCheckboxGroup's `<legend>` holds the row minus `mb-1.5`, which is why the row is composed from one const). `eyebrow` is a **composition root, never a call-site class**: its three tiers (`eyebrow-hero`/`eyebrow-panel`/`eyebrow-label`) replaced 22 sites whose comment claimed "deliberately varied" size+tracking and which measured out as exactly three fixed combinations, two of them off-scale bracket values. **`/admin` opts out of the public site's conventions deliberately** — bare `hover:` (all 26 in the repo), `text-[10px]`, `bg-white/NN` — because it is staff-only and carries its own `focus-visible:ring-*` chips; the opt-out is stated here because nothing in the code distinguishes it from rot. → [styling](docs/styling.md)
- **Raised frosted surfaces share a `@utility glass` base**; variants (`glass-nav`/`glass-card`/`glass-btn`) `@apply glass` + deltas. A Tailwind v4 `@apply` **inlines styles but never adds the applied class name** — a `class="glass-card"` panel carries no `glass-panel` token, so `querySelectorAll('.glass-panel')` matched nothing and the sheen silently missed every panel (#108). Fix + rule: the sheen selects **structurally** — `[class*="glass-"]:not(.glass-field):not(.glass-menu)` (`glass-sheen.ts`) — but that's a **substring** match, so name new raised surfaces `glass-*` and don't reuse `glass-` in a non-raised token (or extend the `:not(...)`). → [styling](docs/styling.md)
- **The sheen's clip is NEVER rewritten on scroll, and that is two planes (DAR-170)** — it was one fixed overlay whose `clip-path` was rebuilt from every glass rect per scroll frame, which ghosted on mobile: scroll runs on the compositor thread and its events arrive asynchronously and coalesced, so the clip described where the glass **was** (hard edges lagging crisp borders, worse the faster the scroll, every page). Now a **page-flow `absolute` plane at `z-30`** carries a **page-coordinate** clip the browser moves natively in step with the panels, and a **`fixed` plane at `z-70`** carries sticky/fixed glass (nav, dialog) whose viewport rects don't move — anchoring decided **structurally** by an ancestor walk for `fixed|sticky`, not a component list. Four ways to silently bring the bug back: (1) **`clip-path` travels WITH an element's transform**, so moving a clip layer by a JS-written `translate3d(0,-scrollY)` does not get the lag off the scroll path — it only changes which property carries it (that was the first, reverted fix); (2) **never add `transform`/`filter`/`contain`/`will-change` to a plane or ancestor** — the beams are `position: fixed` and stay screen-anchored with zero JS **only because `clip-path` does not create a containing block for a fixed descendant, while all four of those do** (measured); (3) no `overflow: hidden` on a plane (it would clip the fixed beams to the plane's own box — nothing at all for the `height: 0` page plane, which is zero-height so it can't extend scrollable overflow and feed back into its own measurement); (4) keep the page plane **below** the scrim, or a panel scrolled under the nav lights a rectangle over content the scrim exists to dissolve. Also: **"viewport-anchored" means two things on mobile** — the nav is anchored to the LAYOUT viewport, but a hard scroll to top expands the URL bar and moves the VISUAL viewport under it, so `visualViewport` rebuilds the viewport plane only. **CI cannot test any of this** (Playwright's device emulation changes viewport/DPR/UA, not the compositor or scroll delivery) — it was bisected on a real device with a temporary `?glassdiag=` harness. → [styling](docs/styling.md)
- `pnpm preview` runs the built worker on the real Workers runtime (Wrangler), not `vite preview`. → [commands](docs/commands.md)
- **The preview port is derived per checkout, and e2e never reuses a running server (DAR-79)** — `pnpm preview` and `playwright.config.ts` both read `scripts/preview-port.mjs` (main checkout `4173`; each linked worktree a stable slot in 4174–4272, hashed from its path; `PREVIEW_PORT` overrides, and a non-port value is refused rather than ignored). They used to hardcode 4173 each, and Playwright's `reuseExistingServer` defaults **on** locally — so a preview running in a **sibling worktree** answered the whole suite and it came back green for someone else's branch. Reuse is off now (`E2E_REUSE_SERVER=1` opts back in, warning that the results describe whatever is listening), and a busy port names its owner's **pid + cwd**, because the reflex fix is a `pkill` that kills another session's server. Three mechanics worth keeping: the config is re-imported in **every Playwright worker** — by then our own webServer holds the port, so any port check must be gated on `TEST_WORKER_INDEX === undefined` or the suite fails against itself; `workerd` is wrangler's **grandchild**, so kill the **tree root** (killing the socket owner just makes wrangler respawn it) and a SIGKILLed parent leaves it holding the port under `ppid 1` forever — the source of the stale servers, which `preview.mjs` now reaps three ways (forward SIGTERM, SIGKILL a wedged tree, and ask the port whether something outlived the child, since leftovers stop being its descendants the moment it dies). **Finding that tree root by "walk up while the ancestor is node" walks straight OUT of the tree into whatever supervises it** — under vitest that's the test runner, and the reaper SIGTERMed it (a mutation test proved it: `Terminated`, exit 143); the stop condition must be conjunctive, argv[0] **and** a preview-shaped command line; and CI is a main checkout (`.git` is a **directory**, a linked worktree's is a **file**), which is what keeps `test.yml`'s hand-written `ORIGIN=http://localhost:4173` true — pinned by a spec, since one half is YAML. → [commands](docs/commands.md)
- Run `pnpm gen` after changing `wrangler.jsonc` bindings **or `.env.example`** to refresh the `Env` type — generation is **deterministic** (DAR-49): env-var names come from `.env.example` (never `.env`), volatile wrangler output is normalized, and the `check` CI job drift-guards the committed `worker-configuration.d.ts`. Never run `wrangler types` directly. → [deployment](docs/deployment.md)
- **Prod and dev are SEPARATE Turso DBs, one per Cloudflare Worker.** Prod Worker (`main`→darcstar.tech) → prod DB; a **separate preview Worker** (`[env.preview]` in `wrangler.jsonc`, non-prod branches, its OWN Workers Builds trigger running `wrangler versions upload --env preview`) → dev DB; local `.env` → dev DB. Each Worker holds its own `DATABASE_*` secret, so `getDb()` has **no** env logic — isolation is at the secret layer. Only the **bare** `…-preview.…workers.dev` host mounts `/api/auth/*` (ORIGIN is one value); per-branch preview URLs 404 there. First-time split runbook + the preview Worker's own secrets are in [deployment](docs/deployment.md#environments--databases). → [deployment](docs/deployment.md)
- **A Workers Build deploys the Worker it is CONNECTED to, whatever the config says — so an `[env.*]` block is inert without a trigger of its own (DAR-131)** — every build passes `WRANGLER_CI_OVERRIDE_NAME`, and wrangler obeys it (`Failed to match Worker name … Overriding using the CI provided Worker name`), so the prod-connected build ran `--env preview` while uploading versions of **production**: preview `vars` applied, production **secrets** retained, every feature-branch preview URL reading and writing the **production** database. Five things worth keeping: (1) the ticket's diagnosis was that the deploy command "was never changed from the default" and it was **already** `--env preview` — the flag was never the gate, so the fix is a second build trigger bound to the preview script plus deleting the prod Worker's non-prod trigger, and the runbook's "or let Workers Builds create the Worker" was false for the same reason (a connected build cannot create a differently-named one); (2) the ticket also read a `302` on a preview URL as DAR-81's ORIGIN mismatch, and it was **Cloudflare Access** — an app on `*-darcstar-technologies-website.darcstar.workers.dev` — which both narrowed the hazard (the prod-DB previews were login-gated, not open) and, because the preview Worker's hosts end `-website-preview.` and miss that pattern, is why the provisioned Worker is publicly reachable; **measure the redirect, don't infer the cause from the status**; (3) `versions upload` never shifts traffic, so production itself was never at risk — the damage was confined to what those URLs could read and write; (4) only the **bare** preview host mounts `/api/auth/*`, since `ORIGIN` is a single value matched against the request origin, so per-branch URLs are for looking at the site and the bare host is the auth/limiter probe target — its DB-backed limiter binding (a 429 with `x-retry-after: 3600` on the 4th sign-up POST) is what proves the dev DB is live, a stronger check than any page rendering; (5) "is this Worker deployed?" is not a question a test can ask, so the checkable half is the repo's: the Worker names live once in `auth-options.ts` (with `trustedOrigins` derived from them — the preview wildcard is NOT covered by the prod one, a near-miss that reads as covered), and `preview-worker.spec.ts` pins them against `wrangler.jsonc`, **`[env.preview]`'s existence asserted first** so the ORIGIN and `assets` checks can't pass vacuously against the very state DAR-131 found. Its comment stripper is string-aware because every value it checks is a URL and a naive `//` strip eats `https://`. → [deployment](docs/deployment.md)
- Changing the DB schema? Run `pnpm db:generate` + commit the `drizzle/` migration — the **`drizzle` CI check** (+ a pre-commit hook) regenerates offline and fails on drift, gating merge→prod. **Dev DB** applies via `pnpm db:push`; **prod DB** applies via the **`deploy-prod` GitHub Action** which `pnpm db:migrate`s **then** `wrangler deploy`s on push to `main` (`PROD_DATABASE_*` + `CLOUDFLARE_API_TOKEN`/`CLOUDFLARE_ACCOUNT_ID` secrets), so a failed migration **blocks the deploy** (migrate-before-deploy; Workers Builds does previews only, prod auto-deploy disabled) — never `db:push` prod. An existing `db:push` prod DB needs a one-time `pnpm db:baseline` so migrate is forward-only (skips replaying `0000`). → [deployment](docs/deployment.md)

- **All UI copy lives in Paraglide messages** (`messages/*.json`); the `local/no-raw-text` ESLint rule blocks hardcoded `.svelte` text/attrs (Wordmark exempt). `es` is untranslated → non-base locales are `noindex` via `Seo.svelte`'s `TRANSLATED_LOCALES` flag; hreflang deferred until `es` is real. → [i18n](docs/i18n.md)
- **A non-base catalog holds ONLY translated keys (DAR-53)** — `es.json` was a byte-identical copy of `en.json`, so Paraglide compiled two identical bodies per message; omitting a key compiles the base-locale fallback as a free alias (`const es_x = en_x`) with identical output (−39 KB raw / −6.8% of the client bundle, but only −172 B gzipped — the win is parse+cache, not wire). The convention was documented before and drifted anyway, so it's now `message-catalogs.spec.ts`: **never re-add a key equal to the base value** (true even when the translation legitimately matches — omitting renders the same text for less) and **never add a key the base lacks** (Paraglide compiles an orphan's _base_ variant as the quoted key name, so a typo silently no-ops the translation while English still looks right). Nothing warns — there is no message-lint module in `project.inlang/settings.json`. The spec derives its catalogs by glob, but `evidence-boundary`/`safety-language` scan `en`+`es` **by name**, so it also pins the locale set. → [i18n](docs/i18n.md)
- e2e builds + previews the Cloudflare bundle; match the vitest project to your filename (`client` / `server` / `storybook`). **Seven CI checks run on every PR** (lint, commitlint, PR title, migrations in sync, check, unit tests, e2e — DAR-49/DAR-175); **which of them GATE is a branch-protection setting this repo cannot see**, so running ≠ required. Both test suites are **hermetic** (no `.env` in CI), keep new tests that way. → [commands](docs/commands.md)
- **A squash subject has TWO sources, so commit-message linting needs two jobs (DAR-175)** — the repo is `squash_merge_commit_title: COMMIT_OR_PR_TITLE`, so GitHub takes the subject from the branch commit on a single-commit PR and from the **PR title** on a multi-commit one; wagoid reads commits and never sees the title, so that half reached `main` unchecked. Four things worth keeping: (1) the failure is the rare one that lands **where it cannot be repaired** — once the squash commit exists, its message changes only by force-pushing `main`, so the `push: main` commitlint run stays red against that commit forever, unlike every other check here; (2) `subjectPattern: ^(?![A-Z]).*[^.]$` is doing all the work beyond the type — `amannn/action-semantic-pull-request` validates the type and a non-empty subject and **nothing else** (read from its `action.yml` + `src/validatePrTitle.js`, which also requires the pattern to span the subject whole), and the pattern is `.*[^.]$` rather than the docs' `.+$` so a one-character subject still passes, a lower-case first character ruling out all four cases `subject-case` bans plus `subject-full-stop`; (3) the action's **default** type list is `Object.keys(conventional-commit-types.types)`, measured identical to config-conventional's `type-enum` — two independently versioned packages, so agreement rather than a guarantee, but restating the list in the workflow would add a **third** copy, which is strictly worse than reading the one the action already has; (4) `edited` must be added to `on.pull_request.types` — it is not in the default set, and without it a rejected title stays red after the author fixes it, since nothing re-runs until they push a commit and fixing a title involves no commit. Also non-obvious: the action is **not payload-only** — it re-fetches via `pulls.get` because `context.payload` is an event snapshot that goes stale on the next title edit, so `pull-requests: read` is load-bearing and reads as prunable boilerplate. Job names ARE the required contexts, and **running is not gating**: renaming an already-required one is self-limiting (the PR doing it can't merge, `enforce_admins` is on), but **adding** a check is always merge-then-register-by-hand, and nothing in the repo can assert that the second step happened. `header-max-length` stays uncovered on both paths — GitHub appends ` (#N)` — which is DAR-174 and deliberately not pre-empted here, its two fixes differing in which repo changes. The ticket's second half was **already closed**: `check.yml` has drift-guarded `worker-configuration.d.ts` since DAR-49 (mutation-proven — edit `.env.example`, skip `pnpm gen`, the guard fires). → [commands](docs/commands.md)
- **A Playwright `Response` body is a CDP RETRIEVAL, not a buffered copy (DAR-93)** — `await response.text()` on a handle from `waitForResponse` asks Chromium for the bytes at the moment it is called, so an interaction that re-renders between the two can evict the entry and CDP answers `No data found for resource with given identifier`. The waitlist flow-id spec read the auto-invalidation `__data.json` that way and it **blocked two consecutive merges on PRs that touched nothing near it**, the third time reproducing through `retries: 1` as well — so "a retry absorbs it" was a reasonable read of the first sighting and simply false. Four things worth keeping: (1) the fix is **`page.route` + `route.fetch()`**, which performs the request once and hands the bytes to the TEST process where nothing can evict them, making it deterministic rather than merely rarer — the obvious alternative (read the body inside a `page.on('response')` handler) still retrieves over CDP and only narrows the window; (2) the route is registered **immediately before the click**, because registering it earlier can capture some other `__data.json` whose body legitimately carries the original id, and asserting on a JOIN of the captures would then pass while a re-run load minting a FRESH id sat unexamined behind it — hence `invalidations[0]`, indexed; (3) the assertion stays on the **response, never the rendered field**: the field shows what the step RESPONSE echoed, which was always right, so it would pass against the very DAR-75 over-count this exists to catch (mutation-proven — forcing the load to mint a fresh id fails it in 1.4s); (4) the racy shape is specifically **a client-router subresource read after an interaction**, which is why the repo's three other `.text()` calls are fine and were left alone: two read an `APIResponse` (Playwright buffers those) and one reads a navigation document immediately after `goto`. → [commands](docs/commands.md)
- **A red unit run records itself — don't keep the log (DAR-90)** — one run reported `1 failed | 590 passed` through a `grep` pipe and the reflex re-run destroyed the only copy of the name, so the evidence moved into the machine: a reporter (`scripts/vitest-failure-report.ts`, wired at the **root** `test.reporters` — not a per-project option) writes `test-failures/<ISO>-<pid>.json` on a red run and **nothing** on a green one, so anything in that directory is by construction a failure. Four load-bearing properties: the filename is **unique per run**, because the built-in `json`/`junit` reporters take a FIXED `outputFile` and would re-create the exact "re-running destroys it" defect one directory further from the terminal; a **collection error is recorded even with zero failed test cases** (a module throwing at import makes a red run whose `allTests('failed')` is empty — a reporter walking only failed cases writes "no failures" for it, which misleads worse than silence); the report carries the **10 slowest tests of the run**, since `loadavg` alone can't separate "the box was busy" from "the test is broken" but a baseline can; and every entry point is **fail-soft**, because a reporter that throws turns a green run red. One trap: a CLI `--reporter=…` **replaces** the configured list (so `--reporter=verbose`, the flag you'd type while chasing a flake, silently switches recording off, and `--reporter=default` does NOT restore it) — name the module itself as a second `--reporter`, which is what its default export is for. Conformance to vitest's classes is structural — the builder takes minimal interfaces so the spec needs no casts, and the reporter's typed `onTestRunEnd` passing real `TestModule`s is what makes an API drift a `pnpm check` error (mutation-proven). Measuring also **refuted DAR-90's own leading theory**: `preview-port.spec.ts`'s `descendants` runs in **121 ms**, nowhere near its timeout, while the tightest margin is the **browser** projects — the same test measured **914 ms and 2346 ms on one machine** (2.6× run-to-run variance, 2.1× margin against the 5 s default at the slow end), which is why `client`/`storybook` set `testTimeout: 15_000` and `server` keeps the default. → [commands](docs/commands.md)
