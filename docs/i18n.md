# i18n — Paraglide (inlang)

The main non-obvious system in this repo.

- Messages live in `messages/{locale}.json` (`en`, `es`; base `en`), configured in `project.inlang/settings.json`. **All user-facing UI copy lives here** (issue #18) — components carry no hardcoded strings. Keys are flat snake_case with area prefixes (`hero_*`, `pillar_*`, `domain_*`, `footer_*`, `error_*`, `seo_*`, …). A non-base catalog holds **only genuinely translated keys** — `es.json` is empty today (Spanish is on the roadmap, not started); Paraglide falls back to the base locale for any missing key, so a partial `es.json` never breaks the build. See [Only translated keys](#only-translated-keys-in-a-non-base-catalog-dar-53) — this is a rule, with a spec behind it, not a preference.
- The Paraglide Vite plugin compiles them into `src/lib/paraglide/` (generated — do not edit). Import messages as `import { m } from '$lib/paraglide/messages.js'` and call `m.key({ ... })`; runtime helpers come from `$lib/paraglide/runtime`.
- Locale strategy is **`url`**. The pieces that wire this together:
  - `src/hooks.ts` (`reroute`) de-localizes the incoming URL so routing sees a single canonical path.
  - `src/hooks.server.ts` runs `paraglideMiddleware` and injects `%paraglide.lang%` / `%paraglide.dir%` into `src/app.html`.
  - `src/hooks.client.ts` instantiates `Locale` from `src/lib/paraglide.svelte.ts`, a runes class that overrides Paraglide's get/set-locale so setting a locale `goto`s the localized URL.
- To add a language: add the locale to `project.inlang/settings.json` and a `messages/<locale>.json`, then extend the two catalog scanners that name their locales explicitly — `evidence-boundary.spec.ts` and `safety-language.spec.ts` — and update the pin in `message-catalogs.spec.ts` that fails until you have (it is the only thing that can tell you).

## Only translated keys in a non-base catalog (DAR-53)

`messages/es.json` used to be a **byte-identical copy** of `en.json` — the "English placeholder"
convention — so Paraglide compiled two identical function bodies for every one of the 829 messages:

```js
const en_nav_about = () => `About`;
const es_nav_about = () => `About`; // the duplicate
```

Omitting the key compiles the base-locale fallback as a free alias instead — `const es_nav_about = en_nav_about;` — with byte-identical rendered output. Measured by building both ways from a wiped
`.svelte-kit` **and** a wiped `src/lib/paraglide` (paraglide's incremental output differs from a cold
one, which skews an A/B that only wipes the former):

|                     | mirrored | trimmed |               delta |
| ------------------- | -------: | ------: | ------------------: |
| client bundle, raw  |  580,242 | 540,617 | **−39,625 (−6.8%)** |
| client bundle, gzip |  200,445 | 200,273 |        −172 (−0.1%) |
| `/privacy` chunk    |   17,018 |  11,366 |     −5,652 (−33.2%) |
| `/terms` chunk      |    9,609 |   6,794 |     −2,815 (−29.3%) |

**Gzip hides almost all of it**, so this is not a wire-size win: it is ~39 KB less JS to parse and
cache, and one fewer 829-key file to keep in sync.

The rule, guarded by [`src/lib/message-catalogs.spec.ts`](../src/lib/message-catalogs.spec.ts):

- **Never re-add a key whose value equals the base locale's.** Including when the translation
  genuinely is the same string ("Email", "Admin", proper nouns) — omitting it renders the same text
  for less, so "omit it" is always the right answer. The cost is that the file no longer records
  "a human checked this and it matches", which is a translator-workflow concern, not a rendering one.
- **Never add a key the base catalog doesn't define.** Paraglide compiles an orphan's _base_ variant
  as the key name in quotes (`const en_nav_abuot = () => 'nav_abuot'`) — so a typo'd key means the
  translation silently never applies while English still looks fine. No error, no warning: there is
  no message-lint module in `project.inlang/settings.json`, which is also why nothing complained
  while the mirror existed.

That spec also pins the locale set, because `evidence-boundary.spec.ts` and `safety-language.spec.ts`
import their catalogs **by name** and cannot notice a third one.

A translation tool that round-trips the whole catalog (inlang Fink, the Studio) will hand back every
key, translated or not, and the first rule then fails with a long list. Prune rather than hand-edit:

```sh
# Run from the repo root. Compares serialized, like the spec does, so variant objects prune too;
# a key en.json lacks is left alone on purpose — that is an orphan, and it wants a human.
node -e 'const f="messages/es.json",en=require("./messages/en.json"),es=require("./"+f),S=JSON.stringify;
for(const k of Object.keys(es)) if(k!=="$schema" && S(es[k])===S(en[k])) delete es[k];
require("fs").writeFileSync(f, S(es,null,"\t")+"\n")' && pnpm lint
```

## `getLocale()` inside a remote function depends on whether the form hydrated (DAR-173)

Measured against a real preview, three probes with a control:

| probe                                        | `getLocale()` | `event.request.url`   | `event.url`    |
| -------------------------------------------- | ------------- | --------------------- | -------------- |
| native (no-JS) POST from `/es/waitlist`      | **`es`**      | `/waitlist?/remote=…` | `/es/waitlist` |
| native POST from `/waitlist` (control)       | `en`          | `/waitlist?…`         | `/waitlist`    |
| enhanced (hydrated) POST from `/es/waitlist` | **`en`**      | `/_app/remote/<id>`   | `/es/waitlist` |

A remote `form()` renders `action="?/remote=<id>"` — **relative**, so a native submit posts to the
page's own URL and the `/es` prefix survives. The enhanced submit does not use that action: it
`fetch`es `${base}/${app_dir}/remote/<id>` (`@sveltejs/kit/src/runtime/client/remote-functions/form.svelte.js`),
a path with **no locale prefix**.

Kit does pass the page's URL along, in `x-sveltekit-pathname`, and rewrites `event.url` from it
(`respond.js:128`) — but `handleParaglide` (`src/hooks.server.ts`) runs `paraglideMiddleware(event.request, …)`,
and `event.request.url` is the un-prefixed one. So on the enhanced path **`getLocale()` and `event.url`
disagree**, and the locale falls back to base.

Consequences worth knowing before `es` is real:

- **Do not reach for `getLocale()` in a remote function** expecting the visitor's language. It answers
  correctly only for a visitor whose form had not hydrated. Thread an explicit locale (a hidden field)
  instead.
- **Mail does not use it at all** except the contact ack — see below. This was DAR-173: the waitlist
  ack and the DAR-139 updates confirmation are rendered in `baseLocale`, with the parameter **deleted**
  from the builders so a caller cannot supply one. Those two write to an address a stranger may have
  typed, and the confirmation asks a question its recipient must be able to answer. The contact ack
  keeps the request locale deliberately (it is a reply to whoever just wrote in), and therefore still
  carries the hydration caveat above. Guarded by `src/lib/server/email-locale.spec.ts` plus a
  `@ts-expect-error` in each mailer's own spec.
- **The page itself is unaffected.** SSR of `/es/waitlist` is an ordinary GET, and `m.*()` calls with
  no explicit locale resolve the ambient one — so validation errors returned from a remote function
  are still rendered in the visitor's language.

## Keeping copy out of components

A custom ESLint rule — [`eslint-rules/no-raw-text.js`](../eslint-rules/no-raw-text.js), wired in `eslint.config.js` as `local/no-raw-text` (**error**) over `src/routes/**` + `src/lib/components/**` — fails lint on hardcoded human text in `.svelte` templates and in `title`/`alt`/`aria-label`/`placeholder` attributes. It's a **forward guard**: it sees template text + those attributes, not copy hidden in JS string literals (data arrays, `{@render}` snippet args) — migrate those by hand. Dynamic `{m.*()}` and decorative glyphs (`·`, `→`, `©`, empty `alt`) are ignored; `Wordmark.svelte` is exempt (the "DarcStar Technologies" logotype is a proper noun, not translated).

## Untranslated `/es` — noindex until translated (issue #18)

`es` is wired but serves English — every key falls back to the base locale — so `/es` is a duplicate. To keep it out of the index:

- [`Seo.svelte`](../src/lib/components/Seo.svelte) emits `<meta name="robots" content="noindex, follow">` for any non-base locale, keyed off a single `TRANSLATED_LOCALES = [baseLocale]` flag. That same flag gates `og:locale:alternate` (none emitted while `es` is untranslated).
- The old `display:none` per-locale `<a>` anchors in `+layout.svelte` (a poor SEO pattern) were removed.
- **When Spanish is really translated:** fill in `messages/es.json` — **translated keys only**, leaving anything still English out (above) — add `'es'` to `TRANSLATED_LOCALES`, and emit the reciprocal `<link rel="alternate" hreflang>` set (+ `x-default`) — a `TODO` in `Seo.svelte` marks the spot. hreflang is deferred until then because pointing it at a `noindex` page is contradictory. Note the flag is a **judgement call, not a key count**: `TRANSLATED_LOCALES` should flip when the locale is coherent enough to index, and a partly-filled `es.json` renders a mix of Spanish and English until then.

**Lesson: `checkJs` is off** (`tsconfig.json`). Paraglide's generated `server.js` does `new Request(request.clone())`, which doesn't type-check against the Cloudflare runtime `Request` global that `worker-configuration.d.ts` injects (its `clone()` return type isn't assignable to its own constructor — harmless at runtime). Both files are generated, so the fix lives in `tsconfig.json`: since there's no hand-written `.js` in the app, we don't type-check `.js` bodies. Importers still get full type safety against Paraglide's inferred API.
